What's under the hood — explained so anyone can follow

A guided tour of the architecture, technologies and engineering decisions behind Accident Report, a production-style incident-management platform I built end to end. Every term has a plain-language explanation and a pointer to where it is used in the real code.

The project at a glance

Accident Report lets transport and airside-operations companies record, review and archive incident investigations — from a phone on the apron or a PC in the office — replacing paper forms and scattered files.

1codebase → web + Android
3user roles + a platform owner
12REST API modules
4export formats: PDF, Word, Excel, ZIP
Ncustomers on one install (multi-tenant)

How the pieces fit together

A request travels left to right. Each box has one job.

Client

React Native + Expo

The screens people use. Same code runs as a website and as an Android app.

Edge

Caddy

Serves the website, forwards /api calls, and handles HTTPS certificates automatically.

Server

Node.js + Express API

Checks who you are, what you may do, then reads or writes data. Generates documents.

Storage

MariaDB + uploads

Relational database for records; a persistent volume for photos and documents.

Safety net: a nightly script dumps the database and uploads, encrypts them, and copies them to a separate Hetzner Storage Box — so losing the server does not mean losing the data.

Glossary of technical terms

Search or filter by area. Each card explains the term in plain words and shows how it is used in this project.

React Native Front end

A framework that lets you build real mobile apps using JavaScript and React, instead of writing separate Android and iOS apps.

In this project: every screen — login, the multi-step investigation form, the dashboards — is a React Native component (v0.79).

Expo Front end

A toolkit around React Native that handles building, running and packaging the app, so you spend time on features rather than tooling.

In this project: Expo 53 runs the dev server, exports the web build, and produces the Android build through EAS Build.

Cross-platform / single codebase Front end

Writing the app once and shipping it on several platforms. Less code to maintain, and every platform gets new features at the same time.

In this project: one codebase becomes the website and the Android app using react-native-web.

Client-side routing Front end

Moving between screens without reloading the whole page, while keeping a "back" history — exactly how a native app feels.

In this project: React Navigation stack with 20+ screens for the form sections, driver data and reports lists.

Role-aware UI Front end

The interface changes depending on who is logged in: each person only sees the menu entries that make sense for their job.

In this project: Operators, Supervisors and Admins each get their own menu and landing screen.

Responsive & safe-area layout Front end

Layouts that adapt to phone, tablet and desktop, and avoid notches, system bars and the on-screen keyboard.

In this project: keyboard-aware forms and safe-area handling were added specifically for the Android build; the admin sidebar stays open on wide screens.

Data visualisation Front end

Turning raw numbers into charts people can read at a glance.

In this project: admin statistics — reports per day, per severity level, rejection reasons, team performance — drawn with recharts and chart-kit.

REST API Back end

A set of web addresses (endpoints) the app calls to fetch or change data, using standard verbs like GET, POST, PATCH and DELETE. It is the contract between the app and the server.

In this project: 12 route modules — auth, users, vehicles, employers, reports, drafts, uploads, stats, mitigation, tenant, platform and admin export.

Node.js & Express Back end

Node.js runs JavaScript on the server; Express is the minimal framework used to define routes and handle requests.

In this project: Express 4 powers the whole API, packaged in a Docker image.

Middleware Back end

Small checkpoints that every request passes through before reaching the real logic — like security guards at a door, each checking one thing.

In this project: authentication, "admin only" checks, rate limiting, tenant resolution and storage-quota enforcement are all middleware.

File upload handling Back end

Receiving photos and documents from the app, validating them and storing them safely on the server.

In this project: multer handles multipart uploads; files are filed per customer and per report, and the quota is checked before accepting each one.

Server-side drafts Back end

Unfinished work is saved on the server, not just on the device, so it survives a phone swap, a crash or switching between phone and PC.

In this project: the "Save Draft" button stores the form on the API; drafts can be resumed later or finalised into a report.

Statistics aggregation Back end

Letting the database do the counting and grouping, so the dashboard receives small ready-made summaries instead of thousands of rows.

In this project: dedicated endpoints for reports by day, by state, by severity bin, rejection reasons, validators and draft ageing.

Relational database (MySQL / MariaDB) Data

Data stored in linked tables (users, vehicles, reports…) with rules that keep it consistent. Ideal when records relate to each other.

In this project: MariaDB 10.11, created from a committed schema.sql plus migration files.

Schema & migrations Data

The schema is the blueprint of the tables; migrations are small scripts that evolve that blueprint safely as the product grows.

In this project: BackEnd/db/schema.sql bootstraps a fresh install; migrations upgrade existing ones.

Multi-tenancy Data

One running installation serving many separate customers whose data never mixes — the model behind most SaaS products.

In this project: every record carries a tenant_id; users, data and uploads are isolated per customer.

Quotas & usage limits Data

Caps on how much a customer may use — here, number of active users and storage in GB — enforced by the server, not just displayed.

In this project: set per customer from the Platform dashboard and applied on the very next request; storage is measured from disk.

Audit history Data

A permanent record of who changed what, when and why — essential for billing disputes and compliance.

In this project: every limit or contract change is logged with before/after values, author, date and reason.

JWT (JSON Web Token) Security

A signed digital "pass" the server gives you after login. The app shows it with each request to prove who you are, without sending your password again.

In this project: sessions use JWTs signed with a secret that is generated per deployment and never committed.

Password hashing (bcrypt) Security

Passwords are never stored as text. They are scrambled with a one-way, deliberately slow algorithm, so even a database leak does not reveal them.

In this project: bcrypt hashes for all accounts; the admin export strips the hash columns entirely.

RBAC — role-based access control Security

Permissions are tied to roles (investigator, supervisor, admin) rather than to individuals, so access is predictable and auditable.

In this project: roles AERO, SUP, ADMIN, plus a separate platform owner — and the role is re-checked against the database on every request, so deactivating a user takes effect immediately.

Rate limiting Security

Restricting how many attempts one client can make in a given time, which blocks password-guessing attacks.

In this project: express-rate-limit protects the login endpoint.

HTTP security headers (Helmet) Security

Extra instructions sent to browsers that switch off common attack tricks such as clickjacking and content sniffing.

In this project: helmet is enabled on the API.

CORS Security

A browser rule deciding which websites may call the API. Locking it down stops other sites from using a visitor's session.

In this project: allowed origins are configurable per deployment.

HTTPS / TLS Security

Encrypts traffic between the user and the server so nobody on the network can read or alter it (the padlock in the browser).

In this project: Caddy obtains and renews certificates automatically.

Encrypted offsite backups Security

Backup copies are encrypted before leaving the server and stored in a different data centre, so a stolen or failed machine cannot expose or lose the data.

In this project: age encryption + rsync over SSH to a Hetzner Storage Box; 14-day retention.

Safe-by-default demo seeding Security

Scripts that can destroy data are given guards that make accidental misuse impossible.

In this project: the demo-data script refuses to run unless DEMO_MODE=1, the database name contains "demo", and no real users exist.

Docker & Docker Compose DevOps

Packages each part of the system (database, API, web server) into an isolated container, so it runs identically on any machine. Compose starts them all together with one command.

In this project: docker compose up -d --build launches MariaDB, the API and Caddy.

Reverse proxy (Caddy) DevOps

A front door that receives all traffic and routes it: website files to the browser, /api calls to the API.

In this project: web and API share one domain, which also avoids cross-origin complications.

VPS hosting & server hardening DevOps

Renting a virtual server and securing it: non-root user, SSH keys only, firewall, automatic security updates.

In this project: Hetzner Ubuntu server, UFW allowing only SSH/80/443, unattended-upgrades enabled.

Backup & restore DevOps

A backup you have never restored is only a hope. Scripts must do both directions and be tested.

In this project: backup.sh, restore.sh and update.sh in deploy/, scheduled with cron.

Environment variables & secrets DevOps

Passwords and keys live in a configuration file outside the code, different for every environment, never in Git.

In this project: .env files, with generated random secrets for the database and JWT.

Isolated demo environment DevOps

A public copy of the product with fake data, fully separate from the real system, so prospects can try it with zero risk.

In this project: its own database, API, uploads and secrets on a subdomain; resets itself nightly.

PDF generation from a template Documents

Filling an official, pre-designed PDF with the data from a report, so output matches the layout the client already uses.

In this project: pdf-lib fills the company template; the result is a paper-ready investigation report.

PDF stamping Documents

Writing extra information onto an existing PDF after the fact — such as an approval stamp.

In this project: when a supervisor approves a report, the PDF receives the "Validated by / Referenced / Reported by" stamp.

Word & Excel export Documents

Producing editable files that office staff can open, adjust and send on.

In this project: docx builds Word reports; admin tables and the whole database export to .xlsx (one sheet per table).

ZIP bundling Documents

Packaging a report with its evidence into one download.

In this project: each completed report downloads as a ZIP containing the PDF and its attachments, organised in numbered folders.

Incident investigation workflow Domain

A structured process: record what happened, analyse why, decide actions, then have a supervisor review and approve.

In this project: operator drafts → submits → supervisor approves or rejects (with a reason) → admin analyses trends.

Root-cause analysis Domain

Looking past the visible event to find the underlying reason, so the same incident does not happen again.

In this project: a dedicated step with type → category → subcategory pickers and a free-text description of contributing factors.

Risk matrix Domain

Rating an event by multiplying how severe it is by how often it happens, giving a single comparable number.

In this project: severity (1–5) × frequency (1–5) = risk level 1–25, which drives the Critical Alerts view.

Mitigation measures Domain

The actions chosen to reduce a risk. A shared, growing library avoids re-typing the same measures.

In this project: pick an existing measure or create a new one; admins maintain the list and see frequency per employer.

SMS score Domain

A running safety-management score per employee that grows with the risk level of the incidents they are involved in.

In this project: approved reports raise it; the dashboard ranks the top employees and groups by region.

Document validity tracking Domain

Keeping expiry dates of licences and permits and renewing them with a history.

In this project: employer validity fields with Renew Validity and Validity History actions.

Supabase Other projects

A hosted back end made of PostgreSQL, authentication, storage and serverless functions — a fast route to a secure SaaS.

In CriptoRadar: email + Google OAuth sign-in and the database.

Row-level security (RLS) Other projects

Rules inside the database that decide, row by row, which records each user may read or change — even if the app code has a bug.

In CriptoRadar: each user can only touch their own watchlists and alerts.

Webhooks & HMAC signatures Other projects

In CriptoRadar: subscription payments are confirmed through HMAC-verified webhooks.

Edge / serverless functions Other projects

Small pieces of server code that run on demand, with no server to manage — good for scheduled jobs.

In CriptoRadar: a function emails price alerts on a cron schedule.

LLM integration Other projects

Calling a large language model from your own product to summarise, analyse or transcribe.

In SummaryAI: Node/Express backend calling GPT-4o via OpenRouter; in CriptoRadar: AI market analysis.

Native Android (Kotlin, Jetpack Compose) Other projects

Building an Android app in the platform's own language and UI toolkit, for the most native feel.

In SummaryAI: Compose UI with Retrofit for networking.

Engineering decisions worth noting

Choices that show how the system was designed, not just which libraries were installed.

Trust the database, not the token

A JWT can outlive a user's access. The API re-reads the user's role and status from the database on every request, so removing someone is instant.

Enforce limits on the server

User and storage quotas are checked by the API at the moment of the action. Hiding a button in the UI would be cosmetic; this cannot be bypassed.

One codebase, honest platform limits

Admin tooling is deliberately web-only; the Android app shows a clear notice instead of a cramped dashboard. Fewer screens to maintain, a better experience on each device.

Drafts live on the server

Investigations take time and happen in the field. Server-side drafts mean no lost work and the ability to continue on another device.

Backups that survive losing the server

Local backups are not enough. Encrypted copies go to a different data centre, and the restore path is scripted and meant to be tested.

Demo that cannot touch production

A separate stack with fictional data, reset nightly, and a seeding script with triple safety guards — so showing the product never risks real records.
